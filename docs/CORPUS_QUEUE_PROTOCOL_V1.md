# Черга виділення кандидатів — протокол v1

Мета кроку: зробити стадію читання корпусу відновлюваною та вимірюваною.
Цей крок не означає завершення деривації, локалізації чи редагування статей.

## Контракт

Окрема SQLite з plans, jobs, events не змінює основну базу енциклопедії.
План прив'язаний до work_id, хешу оригіналу, хешу карти зон, профілю
екстракції та параметрів вікон. Зміна цих значень створює новий план
із нульовим покриттям; історія старого залишається. Повторна підготовка
того самого плану не створює дублікатів і не стирає результати.

Ціль — усі body-діапазони карти, прив'язаної source_sha256 до тексту.
Межі перевіряються на включення у файл, UTF-8 та неперетин. Розмір вікна
визначається в символах, але завдання і покриття зберігаються в байтах.
Короткий кінцевий фрагмент не відкидається. Зміст і проміжки між body
не включаються. Покриття = довжина об'єднання done-діапазонів / цільові байти.

Стани: pending → running → done/error. Атомарний claim видає унікальний
token і lease на 900 секунд. Прострочений lease переходить у error та може
бути повторений; не більше трьох спроб на завдання. Старий token не може
завершити завдання нового виконавця. Lease не є глобальним GPU-lock:
спільний GPU розклад потрібно врахувати перед паралельними воркерами.

Worker виконує не більше max_windows спроб за виклик і зупиняється на
першій помилці. Результат кандидатів та стан done записуються однією
транзакцією. Порожній валідний список — успішне читання; транспортна
помилка, неправильний JSON, дрейф джерела чи прострочений lease — ні.
Події claim, lease_expired, done/error залишаються в журналі.

## Підключення

Нова точка входу AutoResearchRunner.run_extraction_cycle і окремий CLI
працюють із чергою. Старий run_single_cycle та кнопка Streamlit залишаються
попереднім конвеєром; їх автоматично не перенаправляли на іншу семантику.
Збережені кандидати очікують наступної стадії локалізації й деривації.

`plan` читає всі доступні твори основної БД без обмеження першими 100;
не викликає LLM. Профіль unassigned-model означає лише планування.
`run` вимагає явні work-id і model, фіксує digest локальної моделі та хеш
клієнта в профілі. Digest тегу звіряється до й після кожного запиту; це
перевірка спостережуваного стану сервера, не блокування сторонніх змін.
Прямий API run_extraction_cycle потребує належно зафіксованого profile
від викликача. Плани різних профілів не сумуються як єдине покриття твору.

```powershell
python scripts/corpus_queue.py plan --queue data/corpus_queue.db
python scripts/corpus_queue.py status --queue data/corpus_queue.db
python scripts/corpus_queue.py run --queue data/corpus_queue.db --work-id 15 --model qwen3.5:27b --max-windows 1
```

## Предметний прогін цього кроку

До запуску фіксуємо виконавця й цей протокол комітом. Створюємо нову
чергу в .benchmarks і плануємо всі доступні тексти. Повторний plan має
залишити кількість завдань і нульове покриття незмінними. Зберігаємо звіти
та хеші. LLM, GPU й мережу в цьому предметному прогоні не використовуємо.
Реальне модельне виконання буде окремим обмеженим експериментом.

Тести до прогону: відновлення з іншого екземпляра черги; Unicode й
перекриття; кілька body-зон; завершення короткого хвоста; lease/recovery;
стеля повторів; дрейф джерела; ідемпотентність; неправильні відповіді LLM.
